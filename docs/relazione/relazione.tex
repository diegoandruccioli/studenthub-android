% ── SOMMARIO ────────────────────────────────────────────────
\chapter*{Sommario}

StudentHub è un'applicazione Android per la gestione della carriera universitaria.
Lo studente registra i propri esami (nome, voto, CFU, data), consulta statistiche
sulla propria carriera accademica (media ponderata, media aritmetica, CFU totali,
proiezione della base di laurea) e monitora i propri progressi attraverso un sistema
di gamification: ogni esame superato genera punti esperienza (XP) calcolati dal server,
contribuisce all'avanzamento di livello e può sbloccare badge tematici.

L'applicazione è sviluppata interamente in Kotlin adottando Clean Architecture
multi-modulo, pattern MVVM con ViewModel e StateFlow, persistenza locale con
Room e DataStore, comunicazione REST tramite Retrofit e OkHttp, background
processing con WorkManager e interfaccia utente dichiarativa realizzata con Jetpack Compose.

La relazione è strutturata come segue: il Capitolo~1 presenta obiettivi e requisiti;
il Capitolo~2 illustra le scelte progettuali e le librerie adottate; il Capitolo~3
descrive i dettagli implementativi più significativi con il formato
Problema--Soluzione; il Capitolo~4 valuta punti forti e punti deboli del progetto;
il Capitolo~5 propone migliorie e sviluppi futuri.

\chapter{Obiettivi e Requisiti}

\section{Descrizione del Progetto}

StudentHub nasce dall'esigenza di offrire allo studente universitario uno strumento
unico per la gestione della propria carriera accademica. Il dominio applicativo
comprende due aree distinte ma interconnesse: la gestione del libretto esami
(registrazione di voto, CFU e data per ciascun esame sostenuto, con calcolo automatico
di media ponderata, media aritmetica, CFU totali accumulati e proiezione della base
di laurea su 110) e la componente di gamification (assegnazione di punti XP a ogni
esame superato secondo la formula \textit{xp = voto × cfu + (lode ? 50 : 0)}
calcolata lato server, avanzamento di livello, sblocco di badge per traguardi raggiunti
e classifica degli studenti).

La logica di calcolo XP risiede esclusivamente nel backend Node.js, eliminando
duplicazioni e garantendo che i dati mostrati sull'app siano sempre allineati
con quelli ufficiali. L'applicazione è progettata per funzionare in modalità
offline-first: le operazioni sul libretto sono disponibili anche senza connessione
di rete e vengono sincronizzate con il server quando la connettività è ripristinata.

\section{Requisiti Funzionali}
\begin{itemize}
    \item Registrarsi con nome, cognome, e-mail e password per creare un nuovo account.
    \item Accedere con e-mail e password; la sessione viene ricordata tra un'apertura e l'altra dell'app.
    \item Visualizzare il libretto con la lista di tutti gli esami registrati, ordinati per data.
    \item Aggiungere un esame specificando nome, voto (18--30 con possibilità di lode), CFU e data.
    \item Eliminare un esame dal libretto.
    \item Visualizzare le statistiche della propria carriera (media ponderata, CFU totali, base di laurea, grafico andamento voti).
    \item Monitorare il completamento degli obiettivi di gamification e i punti XP guadagnati.
    \item Personalizzare le impostazioni dell'account (tema di colorazione dei voti, soglie RGB) nella schermata Profilo.
    \item Effettuare il logout dalla schermata Profilo; la sessione viene invalidata sia localmente che sul server.
    \item Modificare un esame già inserito aggiornandone nome, voto, CFU o data.
    \item Ricevere una notifica locale quando la propria posizione in classifica cambia (sia in miglioramento che in peggioramento).
\end{itemize}

\section{Requisiti Minimi del Corso}

I requisiti minimi obbligatori del corso Sistemi Mobili sono soddisfatti dall'applicazione
nei seguenti punti:

\begin{itemize}
    \item \textbf{Kotlin puro}: l'intero progetto è scritto in Kotlin; non è presente alcun file Java.
    \item \textbf{Separazione in moduli}: il codice è organizzato nei moduli \texttt{:domain},
          \texttt{:data}, \texttt{:ui} e \texttt{:app}, ciascuno con responsabilità distinte.
    \item \textbf{ViewModel e StateFlow}: ogni schermata utilizza un ViewModel dedicato
          come unico state holder; la UI osserva uno \texttt{StateFlow}
          tramite \texttt{collectAsStateWithLifecycle()} e non contiene logica di business.
    \item \textbf{Kotlin Coroutines}: tutte le operazioni di I/O (Room, chiamate di rete) avvengono
          su \texttt{Dispatchers.IO}; il Main Thread non viene mai bloccato.
    \item \textbf{Jetpack Compose}: l'interfaccia utente è implementata interamente in Jetpack
          Compose. Le liste di dati usano \texttt{LazyColumn} con chiave stabile per item,
          equivalente Compose di RecyclerView con DiffUtil.
    \item \textbf{Storage locale}: Room per la persistenza strutturata del libretto esami e dei
          dati di gamification; DataStore per le preferenze utente e i flag di onboarding.
    \item \textbf{Networking}: comunicazione REST con backend Node.js tramite Retrofit e OkHttp;
          autenticazione via cookie JWT HTTP-only con refresh automatico.
    \item \textbf{Background services}: WorkManager per la sincronizzazione offline degli esami
          e il controllo periodico del rank in classifica.
    \item \textbf{Runtime permission}: richiesta di \texttt{POST\_NOTIFICATIONS} (Android~13+)
          con dialog di rationale contestuale prima dell'invio della notifica.
    \item \textbf{Relazione finale}: questo documento.
\end{itemize}

\chapter{Scelte Progettuali}

\section{Architettura del Sistema}

\subsection{Clean Architecture Multi-Modulo}

Il progetto è strutturato in quattro moduli Gradle distinti, ciascuno con
responsabilità ben definite e dipendenze unidirezionali verso i layer inferiori.

\textbf{Modulo \texttt{:domain}} --- nucleo dell'applicazione. Contiene i modelli
di dominio (\texttt{Esame}, \texttt{User}, \texttt{Settings}, \texttt{GamificationStatus}),
le interfacce dei repository (\texttt{EsameRepository}, \texttt{AuthRepository},
\texttt{GamificationRepository}, \texttt{SettingsRepository}) e i Use Cases, ciascuno
con una sola responsabilità (\texttt{AddEsameUseCase}, \texttt{LoginUseCase},
\texttt{GetStatisticheUseCase}, ecc.). Il modulo è \emph{puro Kotlin}: non importa
nessuna classe Android, il che lo rende compilabile ed eseguibile in isolamento
su qualunque JVM. Questo è il principale vantaggio pratico: i test unitari dei
Use Cases e dei calcoli di business logic non richiedono un emulatore Android.

\textbf{Modulo \texttt{:data}} --- implementa le astrazioni definite in \texttt{:domain}.
Contiene le \texttt{@Entity} Room e i rispettivi \texttt{@Dao}, le implementazioni
dei repository (\texttt{EsameRepositoryImpl}, \texttt{AuthRepositoryImpl}, ecc.),
i client di rete (Retrofit API service, OkHttp con \texttt{PersistentCookieJar} e
\texttt{TokenAuthenticator}), i \texttt{DataStore} per preferenze e sessione, e i
\texttt{CoroutineWorker} di WorkManager. Nessuna Entity Room viene mai esposta al
di fuori di questo modulo: i mapper traducono Entity$\leftrightarrow$DomainModel al confine del layer.

\textbf{Modulo \texttt{:ui}} --- layer di presentazione realizzato interamente in
Jetpack Compose. Contiene i composable di schermata (\texttt{LibrettoScreen},
\texttt{StatisticheScreen}, \texttt{ObiettiviScreen}, \texttt{ProfiloScreen},
\texttt{LoginScreen}, \texttt{RegisterScreen}), i ViewModel e le sealed class
di stato UI (\texttt{LibrettoUiState}, \texttt{ProfiloUiState}, ecc.).
I ViewModel dipendono solo dalle interfacce del modulo \texttt{:domain}: non
importano mai classi Room o Retrofit direttamente.

\textbf{Modulo \texttt{:app}} --- punto di ingresso. Contiene \texttt{CustomApplication}
che implementa l'interfaccia \texttt{RepositoryProvider} e istanzia manualmente
tutti i repository, passando il \texttt{Context} necessario a Room e DataStore.
È l'unico modulo che dipende contemporaneamente da tutti gli altri.

\subsection{Schema delle Dipendenze tra Moduli}

\begin{verbatim}
:app  -->  :ui, :domain, :data
:ui   -->  :domain
:data -->  :domain
:domain --> (nessuna dipendenza interna)
\end{verbatim}

La freccia \texttt{:ui $\to$ :domain} e l'assenza di \texttt{:ui $\to$ :data}
sono la scelta progettuale più rilevante: il layer UI non può mai accedere
direttamente al database o al client di rete. Qualunque operazione sui dati
deve passare obbligatoriamente per un Use Case. Questa regola è applicata
strutturalmente dal sistema di build di Gradle: un tentativo di importare
una classe Room da un composable produrrebbe un errore di compilazione.

La freccia \texttt{:data $\to$ :domain} significa che le implementazioni
dei repository dipendono dalle interfacce definite nel dominio, non viceversa
(Dependency Inversion Principle): sostituire Room con un'altra soluzione di
persistenza richiederebbe modifiche solo in \texttt{:data}, lasciando intatti
\texttt{:domain} e \texttt{:ui}.

\subsection{Pattern MVVM e Flusso dei Dati}

Il flusso di un'azione utente procede in senso discendente attraverso i layer:

\begin{lstlisting}[language={},basicstyle=\ttfamily\small]
Composable --(evento)--> ViewModel
    --> UseCase --> Repository (interfaccia)
                         |
                  RepositoryImpl --> Room DAO / Retrofit
\end{lstlisting}

Il flusso reattivo dei dati procede in senso ascendente:

\begin{lstlisting}[language={},basicstyle=\ttfamily\small]
Room DAO: Flow<List<EsameEntity>>
    --> RepositoryImpl: map + flowOn(Dispatchers.IO)
    --> UseCase: trasformazioni business
    --> ViewModel: stateIn(viewModelScope, Eagerly|WhileSubscribed)
                   --> StateFlow<UiState>
    --> Composable: collectAsStateWithLifecycle()
\end{lstlisting}

La UI non interroga mai attivamente i dati: osserva uno \texttt{StateFlow}
e si ridisegna per recomposition ogni volta che lo stato cambia.
Il ViewModel sopravvive ai cambi di configurazione (rotazione schermo,
ridimensionamento finestra) grazie al meccanismo di Jetpack: la connessione
al database Room non viene interrotta e lo stato dell'interfaccia viene
preservato senza richiedere logica aggiuntiva.

\section{Gestione reattiva della lista esami}

\paragraph{Problema}
La lista degli esami deve aggiornarsi automaticamente ogni volta che un esame viene
aggiunto o eliminato, senza che la UI debba interrogare manualmente il database.
Un'implementazione basata su query one-shot richiederebbe un refresh esplicito
ad ogni operazione, con rischio di inconsistenze. È inoltre necessario evitare
memory leak quando il Fragment viene distrutto in seguito a un cambio di configurazione.

\paragraph{Soluzione}
Il pattern adottato sfrutta la reattività nativa di Room tramite \texttt{Flow}.
Il DAO espone \texttt{fun getAllEsami(): Flow<List<EsameEntity>>}: Room emette
automaticamente una nuova lista ad ogni modifica della tabella \texttt{esami}.
Il \texttt{RepositoryImpl} applica il mapper \texttt{toDomain()} e garantisce
l'esecuzione su \texttt{Dispatchers.IO} tramite \texttt{flowOn}.
Il \texttt{LibrettoViewModel} combina il Flow di Room con due \texttt{StateFlow}
di ordinamento (\texttt{\_sortBy}, \texttt{\_sortOrder}) tramite l'operatore
\texttt{combine()}, esponendo un unico \texttt{StateFlow<List<Esame>>} già ordinato.
Ogni variazione in uno qualunque dei tre flussi sorgente innesca automaticamente
un ricalcolo e una recomposition nella UI:

\begin{lstlisting}
private val _sortBy    = MutableStateFlow(SortBy.DATA)
private val _sortOrder = MutableStateFlow(SortOrder.DESC)

val esami: StateFlow<List<Esame>> = combine(
    getEsamiUseCase(), _sortBy, _sortOrder
) { lista, by, order ->
    val sorted = when (by) {
        SortBy.DATA -> lista.sortedBy { it.dataEsame }
        SortBy.VOTO -> lista.sortedBy { it.voto }
        SortBy.CFU  -> lista.sortedBy { it.cfu }
    }
    if (order == SortOrder.DESC) sorted.reversed() else sorted
}.stateIn(viewModelScope, SharingStarted.Eagerly, emptyList())

init {
    // Carica le impostazioni dal server al login/reinstall: popola il DataStore
    // in modo che observeSettingsUseCase() emetta subito i valori reali
    // dell'account corrente (es. tema RGB) senza aspettare la schermata Profilo.
    viewModelScope.launch { getSettingsUseCase() }
}

fun refreshEsami() {
    viewModelScope.launch { refreshEsamiUseCase() }
}
\end{lstlisting}

Il blocco \texttt{init} non lancia più il caricamento degli esami: quel compito
è delegato alla schermata tramite \texttt{LaunchedEffect(Unit)}, evitando
una doppia chiamata concorrente a \texttt{GET /exams} che poteva causare
una race condition nel pattern \emph{check-then-insert} di \texttt{refreshEsami}.
Il blocco \texttt{init} esegue invece \texttt{getSettingsUseCase()}: al momento
del login (o dopo reinstallazione) il \texttt{SettingsDataStore} è vuoto ---
perché azzerato esplicitamente al logout tramite \texttt{SettingsDataStore.clear()} ---
e senza questa chiamata le impostazioni dell'account (es.\ il tema RGB per i colori dei
voti) verrebbero applicate solo dopo la prima visita alla schermata Profilo.

Il caricamento degli esami avviene invece via \texttt{LaunchedEffect(Unit)} in
\texttt{LibrettoScreen}:

\begin{lstlisting}
LaunchedEffect(Unit) {
    viewModel.refreshEsami()      // ri-fetch dal server al rientro in composizione
    gamificationViewModel.refreshStats()
}
\end{lstlisting}

Questo pattern --- identico a quello adottato in \texttt{ObiettiviScreen} ---
garantisce che ogni volta che la schermata entra in composizione venga eseguita
una chiamata server fresca. Room agisce da cache locale: se i dati sono già
presenti la UI li mostra immediatamente, mentre la chiamata remota aggiorna
eventualmente i dati in background.

Con l'adozione di Jetpack Compose, la UI osserva il \texttt{StateFlow} tramite
\texttt{collectAsStateWithLifecycle()}, che integra automaticamente la consapevolezza
del ciclo di vita: la raccolta si sospende quando la schermata non è visibile e riprende
al rientro in foreground, prevenendo aggiornamenti inutili e memory leak.
La lista degli esami è implementata con \texttt{LazyColumn} e chiave stabile per item
(\texttt{key = \{ it.id \}}): Compose usa la chiave per applicare
la riconciliazione dell'albero delle composizioni, ottenendo lo stesso effetto di
\texttt{DiffUtil.ItemCallback} senza richiedere un Adapter esplicito.

\section{Architettura UI con Jetpack Compose e navigazione adattiva}

\paragraph{Problema}
A partire dall'introduzione di Jetpack Compose nel corso, il layer UI deve adottare
il paradigma dichiarativo. Occorre una struttura di navigazione che si adatti
automaticamente a smartphone, tablet e finestre ridimensionabili su desktop,
senza richiedere layout alternativi per ogni configurazione.

\paragraph{Soluzione}
Il modulo \texttt{:ui} è stato interamente convertito a Jetpack Compose.
\texttt{MainActivity} estende \texttt{ComponentActivity} e delega tutta la UI
a \texttt{setContent \{\}}, con \texttt{enableEdgeToEdge()} per il disegno
sotto le barre di sistema.

Per la navigazione adattiva si utilizza \texttt{NavigationSuiteScaffold} della
libreria \texttt{material3-adaptive-}\texttt{navigation-suite}: questo composable seleziona
automaticamente la modalità di navigazione più appropriata in base alle dimensioni
della finestra --- Bottom Navigation Bar su smartphone in verticale, Navigation Rail
su tablet e in orizzontale, Navigation Drawer su schermi grandi.
Il pattern segue esattamente quello insegnato nel corso e soddisfa il requisito
di responsiveness senza alcun codice condizionale esplicito.

\begin{lstlisting}
NavigationSuiteScaffold(
    navigationSuiteItems = {
        AppDestinations.entries.forEach { destination ->
            item(
                icon = { Icon(destination.icon, ...) },
                label = { Text(destination.label) },
                selected = destination == currentDestination,
                onClick = { currentDestination = destination }
            )
        }
    }
) {
    when (currentDestination) {
        AppDestinations.LIBRETTO     -> LibrettoScreen(viewModel = librettoViewModel)
        AppDestinations.STATISTICHE  -> StatisticheScreen(viewModel = statisticheViewModel)
        AppDestinations.OBIETTIVI    -> ObiettiviScreen(viewModel = obiettiviViewModel)
        AppDestinations.PROFILO      -> ProfiloScreen(viewModel = profiloViewModel)
    }
}
\end{lstlisting}


Tutti i ViewModel dell'applicazione utilizzano il pattern \texttt{ViewModelProvider.Factory}
con dependency injection manuale: il composable ospitante recupera i repository dal
\texttt{RepositoryProvider} (implementato da \texttt{CustomApplication}) e li passa
alla factory. Questo approccio migliora la testabilità --- i ViewModel non dipendono
da \texttt{Application} e possono essere istanziati in unit test con dipendenze
fittizie --- e garantisce un DI omogeneo nell'intero layer UI:

\begin{lstlisting}
val profiloViewModel: ProfiloViewModel = viewModel(
    factory = ProfiloViewModel.provideFactory(
        getSettingsUseCase = GetSettingsUseCase(settingsRepository),
        updateSettingsUseCase = UpdateSettingsUseCase(settingsRepository),
        logoutUseCase = LogoutUseCase(authRepository)
    )
)
\end{lstlisting}

Ogni ViewModel sopravvive ai cambi di configurazione (rotazione schermo,
ridimensionamento finestra su desktop) grazie al meccanismo standard di Jetpack.

\section{Autenticazione e gestione della sessione utente}

\paragraph{Problema}
L'applicazione comunica con un backend REST (Node.js/Express) che autentica tramite
JWT in cookie HTTP-only. L'app deve: (1) presentare le schermate di login e registrazione
finché l'utente non è autenticato; (2) persistere la sessione tra riavvii dell'app;
(3) non bloccare il Main Thread durante le chiamate di rete; (4) tornare
automaticamente al login in caso di sessione scaduta o assente.

\paragraph{Soluzione}
Il network layer è costruito su \textbf{Retrofit\,2 + OkHttp\,4}. OkHttp è configurato
con un \texttt{PersistentCookieJar} (SharedPreferences-backed, descritto nella
Sezione~\ref{sec:cookiejar}), che persiste e reinvia automaticamente il cookie
\texttt{token} a ogni richiesta. Il cookie è HTTP-only: non è mai accessibile
in chiaro dal codice Kotlin.

La persistenza della sessione tra riavvii è affidata a \textbf{DataStore
(Preferences)}: all'avvio il \texttt{AuthViewModel} legge il flag \texttt{is\_logged\_in}
e lo espone come \texttt{StateFlow<Boolean?>} (\texttt{null} = caricamento in corso,
\texttt{false} = non autenticato, \texttt{true} = autenticato):

\begin{lstlisting}
val sessionState: StateFlow<Boolean?> = repository.isLoggedIn()
    .map { it as Boolean? }
    .stateIn(viewModelScope, SharingStarted.Eagerly, null)
\end{lstlisting}

Il composable radice \texttt{RootNavigation} osserva \texttt{sessionState} e decide
quale schermata mostrare senza alcuna navigazione imperativa:

\begin{lstlisting}
when (sessionState) {
    null  -> CircularProgressIndicator() // DataStore non ha ancora emesso
    false -> if (showRegister) RegisterScreen(...) else LoginScreen(...)
    true  -> StudentHubApp()             // NavigationSuiteScaffold con le tab
}
\end{lstlisting}

Quando il backend restituisce una risposta di successo, \texttt{AuthRepositoryImpl}
chiama \texttt{sessionDataStore.setLoggedIn(true)}: il DataStore emette il nuovo valore,
il \texttt{StateFlow} si aggiorna e la UI transita automaticamente verso l'app
senza alcuna chiamata esplicita alla navigazione.

Il logout è implementato con lo stesso pattern dichiarativo. \texttt{LogoutUseCase}
chiama \texttt{POST /api/auth/logout} avvolto in \texttt{runCatching}: anche se
il backend non è raggiungibile, la sessione locale viene comunque invalidata.
In particolare \texttt{AuthRepositoryImpl.logout()} esegue in sequenza:
\texttt{NetworkClient.clearCookies()} (revoca cookie JWT), \texttt{db.clearAllTables()}
(azzera Room: esami, obiettivi, leaderboard), \texttt{RankDataStore.clear()} (azzera
XP/rank/livello), \texttt{SettingsDataStore.clear()} (azzera le impostazioni cached) e
\texttt{setLoggedIn(false)} (reindirizza alla login). Questo garantisce l'isolamento
completo dei dati tra account diversi sullo stesso dispositivo: al successivo login,
nessun dato dell'utente precedente sopravvive in locale.
\texttt{ProfiloViewModel} espone \texttt{isLoggingOut: StateFlow<Boolean>} per
disabilitare il pulsante e mostrare un indicatore di caricamento durante
l'operazione asincrona. Al termine, quando il DataStore emette \texttt{false},
\texttt{RootNavigation} torna alla schermata di login automaticamente --- nessuna
navigazione imperativa richiesta.

\section{Persistenza e rinnovo automatico del cookie JWT}
\label{sec:cookiejar}

\paragraph{Problema}
Il backend autentica le richieste tramite cookie HTTP-only: un access token
(scadenza 15 minuti) e un refresh token (scadenza settimanale). Una
\texttt{CookieJar} solo in memoria perde i cookie a ogni riavvio, forzando
il login manuale. Alla scadenza dell'access token, senza gestione esplicita,
tutte le chiamate API restituiscono 401.

\paragraph{Soluzione}
Il problema è risolto con due componenti nel \texttt{NetworkClient}. Il primo è
\texttt{PersistentCookieJar}: implementazione di \texttt{CookieJar} che serializza
i cookie su \texttt{SharedPreferences} (Gson) e li ricarica all'inizializzazione;
le operazioni sono \texttt{@Synchronized} per la thread-safety di OkHttp e i
cookie scaduti vengono filtrati in \texttt{loadForRequest}. Al logout,
\texttt{clearCookies()} azzera sia la cache in memoria sia le preferenze,
impedendo il riutilizzo della sessione tra utenti diversi sullo stesso dispositivo.

Il secondo è \texttt{TokenAuthenticator}: \texttt{Authenticator} OkHttp che
intercetta ogni risposta 401 ed esegue una chiamata sincrona a
\texttt{POST /api/auth/refresh}. In caso di successo OkHttp ritenta la request
originale in modo trasparente, senza che nessun ViewModel o Use Case gestisca
logica di retry. Se il refresh fallisce, invalida la sessione tramite
\texttt{SessionDataStore.setLoggedIn(false)}: \texttt{RootNavigation} reagisce
reattivamente e porta l'utente al login, senza navigazione imperativa.
Una guardia esplicita previene loop infiniti: se la request fallita è già
\texttt{/auth/refresh}, l'authenticator restituisce \texttt{null} immediatamente.

\section{Sincronizzazione offline-first con WorkManager}

\paragraph{Problema}
L'utente deve poter inserire, modificare ed eliminare esami anche in assenza di connessione
di rete. Queste operazioni offline non devono andare perse e devono essere sincronizzate
con il server non appena la connettività torna disponibile, garantendo la consistenza dei
dati ed evitando problemi derivanti da aggiornamenti parziali o disallineati tra il
database locale e le chiamate di rete.

\paragraph{Soluzione}
Il sistema adotta il \textbf{Transactional Outbox Pattern}. Invece di gestire la coda di
sincronizzazione direttamente tramite flag sulla tabella degli esami, viene introdotta
una tabella dedicata denominata \texttt{action\_outbox} e un enum \texttt{SyncStatus}
con i valori \texttt{PENDING}, \texttt{SYNCED} e \texttt{FAILED}.

Ogni volta che l'utente esegue un'azione di inserimento, modifica o eliminazione, l'app
esegue due operazioni contemporaneamente: aggiorna la tabella \texttt{esami} locale e inserisce
la corrispondente azione di sincronizzazione nella tabella \texttt{action\_outbox}. Queste due
operazioni sono racchiuse all'interno di una singola transazione atomica ACID di Room.
Ciò garantisce la massima consistenza: non si può verificare la situazione in cui l'esame
locale viene salvato ma la richiesta di sincronizzazione non viene registrata (o viceversa),
risolvendo alla radice il rischio di inconsistenza dovuto alla scrittura separata su due
sistemi differenti (il database locale e la coda dei messaggi/rete).

Le azioni inserite nell'outbox contengono il tipo di operazione (aggiunta, modifica, eliminazione)
e i dati dell'esame. \texttt{SyncExamsWorker} viene eseguito periodicamente in background
da WorkManager con vincolo di connessione di rete attiva. Il worker recupera i record
in stato \texttt{PENDING} dall'outbox e li elabora in sequenza cronologica:
\begin{enumerate}
    \item Per le eliminazioni (\texttt{DELETE}), effettua la chiamata remota e in caso di successo
    rimuove definitivamente il record locale. Se il server risponde 404, l'esame è già stato rimosso
    e viene eliminato anche in locale.
    \item Per inserimenti e modifiche (\texttt{ADD}/\texttt{UPDATE}), esegue le richieste POST/PUT. In caso di successo,
    aggiorna lo stato dell'outbox a \texttt{SYNCED}.
\end{enumerate}
In caso di fallimento della chiamata di rete per problemi temporanei, lo stato dell'azione viene
impostato a \texttt{FAILED} e il worker restituisce \texttt{Result.retry()}, innescando il
meccanismo di backoff esponenziale di WorkManager per un tentativo successivo.

Per quanto riguarda il flusso in entrata (\texttt{refreshEsami}), la sincronizzazione dal server
segue una politica di risoluzione dei conflitti a priorità locale: se per un determinato esame
è presente un record non ancora sincronizzato in \texttt{action\_outbox}, la versione locale
ha la precedenza e non viene sovrascritta dai dati provenienti dal server, preservando le modifiche
offline dell'utente.

\section{Notifiche di cambio rank con LeaderboardCheckWorker}

\paragraph{Problema}
L'utente deve ricevere una notifica quando la sua posizione in classifica migliora,
senza tenere l'app aperta. La notifica richiede il permesso \texttt{POST\_NOTIFICATIONS}
(Android~13+) da richiedere a runtime. Il worker deve confrontare il rank attuale
con il precedente riutilizzando la logica di fetch già presente nel repository.

\paragraph{Soluzione}
\texttt{LeaderboardCheckWorker} (CoroutineWorker) è schedulato in
\texttt{CustomApplication} ogni 15 minuti con constraint \texttt{CONNECTED}
e policy \texttt{KEEP} (nessuna schedulazione duplicata). Prima del fetch, il rank
corrente viene letto da \texttt{RankDataStore};
\texttt{GamificationRepositoryImpl}\texttt{.getLeaderboard()}
aggiorna \texttt{RankDataStore} come effetto collaterale tramite \texttt{saveMyRank()}.
Il nuovo rank viene riletto e confrontato: se cambiato (in miglioramento o
peggioramento), viene emessa una notifica con testo differenziato ---
``Rank migliorato!'' con indicazione della nuova posizione se
\texttt{newRank < oldRank}, ``Rank cambiato'' con la nuova posizione se
\texttt{newRank > oldRank}.
In caso di eccezione il worker restituisce \texttt{Result.retry()} per il backoff
automatico di WorkManager. Il permesso \texttt{POST\_NOTIFICATIONS} è richiesto
in \texttt{ObiettiviScreen} con un dialog di rationale; l'utente può rifiutarlo
senza compromettere le funzionalità principali dell'app.

Di seguito viene riportato lo snippet del worker \texttt{LeaderboardCheckWorker}, allineato alla logica reale definita nel codice dell'applicazione:

\begin{lstlisting}
class LeaderboardCheckWorker(
    appContext: Context,
    workerParams: WorkerParameters,
) : CoroutineWorker(appContext, workerParams) {

    private val rankDataStore = RankDataStore(appContext)
    private val repository = GamificationRepositoryImpl(appContext)

    override suspend fun doWork(): Result {
        return try {
            rankDataStore.saveLastCheckTimestamp(System.currentTimeMillis())
            val leaderboardResult = repository.getLeaderboard()
            if (leaderboardResult.isSuccess) {
                Result.success()
            } else {
                Result.retry()
            }
        } catch (e: Exception) {
            Result.retry()
        }
    }
}
\end{lstlisting}

\section{Sincronizzazione dello stato di completamento degli obiettivi}

\paragraph{Problema}
Il backend espone due endpoint distinti per la gamification: \texttt{GET /gamification/badges}
restituisce il catalogo completo degli obiettivi con i soli campi anagrafici
(\texttt{id}, \texttt{nome}, \texttt{descrizione}, \texttt{xp\_valore}), senza alcun
dato utente-specifico; \texttt{GET /gamification/my-badges} restituisce solo gli obiettivi
effettivamente sbloccati dall'utente. Un'implementazione che interroghi unicamente il
primo endpoint non è in grado di determinare quale obiettivo risulti completato:
il campo \texttt{completato} è sempre assente dalla risposta del catalogo e Gson lo
deserializza come \texttt{null}, rendendo ogni obiettivo permanentemente non completato
nella UI anche dopo che il server ha assegnato i relativi punti XP.

\paragraph{Soluzione}
\texttt{ObiettivoRepositoryImpl.refreshObiettivi()} chiama entrambi gli endpoint in
sequenza, costruisce un \texttt{Set<Int>} degli identificativi degli obiettivi sbloccati,
quindi effettua il merge: per ogni voce del catalogo, \texttt{completato} viene impostato
a \texttt{true} se e solo se il suo identificativo è presente nel set degli sbloccati.

\begin{lstlisting}
override suspend fun refreshObiettivi(): Result<Unit> = withContext(ioDispatcher) {
    runCatching {
        val allBadges = api.getBadges().body() ?: emptyList()
        val myBadgesResponse = api.getMyBadges()
        val completedIds: Set<Int> = if (myBadgesResponse.isSuccessful)
            myBadgesResponse.body()?.map { it.safeId }?.toSet() ?: emptySet()
        else emptySet()

        val entities = allBadges.map { dto ->
            ObiettivoEntity(
                id = dto.safeId, nome = dto.nome,
                descrizione = dto.descrizione,
                completato = dto.safeId in completedIds,
                premioXp = dto.xpValore
            )
        }
        if (entities.isNotEmpty()) obiettivoDao.insertAll(entities)
    }
}
\end{lstlisting}

Il pattern è identico a quello adottato nel frontend web (Vue\,3 + Pinia), dove
\texttt{Promise.all} esegue le due fetch in parallelo e la computed property
\texttt{badgesWithUnlockStatus} effettua lo stesso controllo di appartenenza al set.
Poiché \texttt{refreshObiettivi()} viene invocato da \texttt{LibrettoViewModel} dopo
ogni operazione CRUD sugli esami, il Flow esposto da Room aggiorna automaticamente
la UI degli obiettivi senza alcuna navigazione o refresh manuale.

\section{Architettura reattiva del layer gamification}

\paragraph{Problema}
La schermata Obiettivi aggrega dati da sorgenti eterogenee: XP, livello e rank
dell'utente (in \texttt{RankDataStore}), lista della classifica (cache Room) e
lista degli obiettivi (Room). È necessario combinare queste sorgenti in un unico
stato UI coerente, aggiornato reattivamente senza polling.

\paragraph{Soluzione}
\texttt{GamificationViewModel} usa \texttt{combine()} per fondere quattro Flow in
un unico \texttt{StateFlow<GamificationUiState>}: \texttt{getGamificationDataUseCase()}
(che combina sette chiavi di \texttt{RankDataStore} in uno \texttt{UserStats}),
\texttt{getLeaderboardUseCase()} (Flow da Room), \texttt{\_errorMessage} e
\texttt{\_isLoading}. Il metodo \texttt{refreshAll()} lancia in parallelo le due
chiamate di rete tramite \texttt{async}, riducendo il tempo di attesa al massimo
delle due:

\begin{lstlisting}
val uiState: StateFlow<GamificationUiState> = combine(
    getGamificationDataUseCase(), // UserStats da RankDataStore
    getLeaderboardUseCase(),      // List<LeaderboardEntry> da Room
    _errorMessage,
    _isLoading
) { stats, leaderboard, error, isLoading ->
    when {
        error != null -> GamificationUiState.Error(error)
        isLoading     -> GamificationUiState.Loading
        else -> GamificationUiState.Success(
            stats = stats,
            leaderboard = leaderboard.sortedByDescending { it.xpTotali }
        )
    }
}.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000),
          GamificationUiState.Loading)
\end{lstlisting}

Qualunque aggiornamento in una sorgente (es.\ un esame inserito che modifica XP
o rank) si propaghi automaticamente alla UI senza refresh manuali.

\section{Rendering dichiarativo e performante del grafico carriera}

\paragraph{Problema}
La visualizzazione dell'andamento accademico (\texttt{StatisticheScreen}) richiede un grafico
lineare capace di mostrare l'evoluzione dei voti nel tempo e la proiezione della media fissa.
L'inclusione di librerie di charting di terze parti avrebbe appesantito inutilmente l'APK e
infranto il paradigma puramente dichiarativo di Compose. Era inoltre necessario gestire le
animazioni di ingresso senza causare pesantezza sul Main Thread e senza ricalcoli con alta potenza di calcolo
delle coordinate spaziali ad ogni frame.

\paragraph{Soluzione}
Il grafico è stato implementato custom sfruttando le API di disegno nativo \texttt{Canvas} di
Jetpack Compose. L'architettura del componente \texttt{CareerChart} si basa su un approccio
a strati (Z-Order) pre-calcolato:
1. \textbf{Mappatura univoca:} I dati di dominio (\texttt{OffsetRelativo})
vengono mappati in coordinate pixel assolute una singola volta all'interno dello scope di disegno,
garantendo coerenza topologica tra i punti dei voti e la curva di media ponderata.
2. \textbf{Animazione reattiva:} L'ingresso del grafico è governato da un \texttt{Animatable}
che interpola un valore da 0f a 1f in 1500ms. Questo valore moltiplica i path vettoriali
e l'opacità dei layer.
3. \textbf{Gestione dello strato visivo:} Il disegno avviene in ordine: prima la griglia
di background, poi l'area del gradiente tramite \texttt{Brush.verticalGradient}, la curva creata dinamicamente interpolando i nodi con \texttt{cubicTo}, e infine il layer
in foreground con le annotazioni.

\begin{lstlisting}
// Animazione
val animationProgress = remember { Animatable(0f) }
LaunchedEffect(puntiVotiRelativi) {
    animationProgress.animateTo(1f, animationSpec = tween(durationMillis = 1500))
}

Canvas(modifier = modifier) {
    val progress = animationProgress.value
    // calcolo margini e coordinate

    // Area riempita con sfondo
    drawPath(
        path = fillPath,
        brush = Brush.verticalGradient(
            colors = listOf(errorColor.copy(alpha = 0.2f * progress), Color.Transparent),
            startY = pointsMedia.minOf { it.y },
            endY = height - margin
        )
    )
}
\end{lstlisting}

Questo approccio garantisce 60 FPS stabili durante l'animazione, poiché la recomposition
non viene triggerata: la variazione di \texttt{animationProgress.value} invalida unicamente
la fase di \textit{Draw} del ciclo di vita di Compose, by-passando le fasi di \textit{Composition}
e \textit{Layout}.

\section{Gestione dello stato durante operazioni asincrone nella UI}

\paragraph{Problema}
Durante il salvataggio delle impostazioni nella \texttt{ProfiloScreen}, il ViewModel
transita attraverso uno stato intermedio. Una prima implementazione usava uno stato
\texttt{Saving} privo di dati e recuperava le impostazioni correnti accedendo
direttamente a \texttt{viewModel.uiState.value} all'interno del composable.
Questo approccio aggira il meccanismo reattivo di Compose: l'accesso diretto a
\texttt{.value} non registra una dipendenza di recomposition e può restituire
uno snapshot stantio se lo stato cambia tra due riesecuzioni della funzione composable.

\paragraph{Soluzione}
La sealed class \texttt{ProfiloUiState} è stata ristrutturata in modo che ogni
stato porti con sé tutti i dati necessari alla UI, eliminando qualsiasi accesso
diretto al flusso dello stato:

\begin{lstlisting}
sealed class ProfiloUiState {
    object Loading : ProfiloUiState()
    data class Success(val settings: Settings) : ProfiloUiState()
    data class Saving(val previousSettings: Settings) : ProfiloUiState()
    data class Error(val message: String, val settings: Settings? = null) : ProfiloUiState()
}
\end{lstlisting}

Quando l'utente avvia il salvataggio, il ViewModel transita a \texttt{Saving(settings)}
portando le impostazioni correnti. Il composable mostra il form disabilitato con
un \texttt{CircularProgressIndicator} nel bottone senza dover accedere ad altri
\texttt{StateFlow}. Al termine dell'operazione il ViewModel emette \texttt{Success(settings)}
(o \texttt{Error}): la UI si aggiorna per recomposition in modo interamente reattivo.

\paragraph{Problema}
La correttezza dei calcoli statistici (\texttt{GetStatisticheUseCase}) non può essere

\section{Deserializzazione della data esame dal backend}

\paragraph{Problema}
Il campo \texttt{data} restituito dall'endpoint \texttt{GET /api/exams} non è una stringa
\texttt{DATE} pura (\texttt{"2026-05-25"}) ma una stringa ISO~8601 completa
(\texttt{"2026-05-25T00:00:00.000Z"}), prodotta dalla libreria \texttt{mysql2} di Node.js
quando la colonna MySQL è di tipo \texttt{DATE} e l'opzione \texttt{dateStrings: true}
non è attiva. La chiamata \texttt{LocalDate.parse(dto.data)} di Java Time solleva una
\texttt{DateTimeParseException} perché il formatter predefinito si aspetta esattamente
dieci caratteri nel formato \texttt{yyyy-MM-dd}. L'eccezione era inghiottita da un
\texttt{runCatching} in \texttt{refreshEsami()}: Room restava vuota senza alcun messaggio
di errore visibile, rendendo il bug particolarmente difficile da diagnosticare.

\paragraph{Soluzione}
Poiché il backend non è modificabile, la correzione è applicata lato Android:

\begin{lstlisting}
val remoteDate = LocalDate.parse(dto.data.take(10))
\end{lstlisting}

\texttt{String.take(10)} estrae i primi dieci caratteri (\texttt{"2026-05-25"})
prima del parsing, eliminando il suffisso temporale indipendentemente dal formato
esatto prodotto dal backend. L'operazione è sicura anche nel caso in cui il backend
venisse corretto in futuro e tornasse a inviare solo la data: \texttt{take(10)} su
una stringa di dieci caratteri restituisce la stringa invariata.

\section{Allineamento dei valori ENUM tema\_voti tra Android e MySQL}

\paragraph{Problema}
La colonna \texttt{tema\_voti} nel database MySQL è definita come
\texttt{ENUM('DEFAULT', 'RGB')}. L'app Android inviava i valori \texttt{"STANDARD"} e
\texttt{"LODE"} non presenti nell'ENUM: MySQL in strict mode rifiuta l'inserimento con
un errore~500, che compariva in UI come \emph{"salvataggio impostazioni fallito"}.
Parallelamente, la strategia di aggiornamento era difettosa: \texttt{updateSettings()}
inviava prima la richiesta al server e aggiornava il DataStore solo in caso di successo.
Ciò significava che un errore di rete transitorio annullava la preferenza locale
dell'utente, anche se l'app funzionava correttamente offline.

\paragraph{Soluzione}
Sono stati applicati due interventi distinti. Il primo allinea i valori inviati
all'ENUM del backend: i valori selezionabili nella \texttt{ProfiloScreen} sono
ora \texttt{"DEFAULT"} e \texttt{"RGB"}; la voce \texttt{"LODE"} è rimossa dal
dropdown e dai valori di fallback in tutti i ViewModel e nei test.
Il secondo corregge la strategia di persistenza in \texttt{SettingsRepositoryImpl}:
il DataStore viene aggiornato \emph{prima} della chiamata API; la chiamata al server
è effettuata in un \texttt{runCatching} separato il cui esito viene ignorato.
In questo modo l'utente vede immediatamente il risultato del salvataggio locale,
e la sincronizzazione remota avviene in modo best-effort senza bloccare l'operazione.
Questa strategia rispecchia il principio offline-first già adottato per il libretto esami.

\section{Deserializzazione del campo \texttt{lode} dal backend}

\paragraph{Problema}
MySQL memorizza il campo \texttt{lode} come \texttt{TINYINT(1)}. La libreria Node.js
\texttt{mysql2} serializza questo tipo come numero intero (\texttt{0} o \texttt{1})
anziché come valore booleano JSON (\texttt{false}/\texttt{true}). Il DTO Android
\texttt{ExamDto.lode} era dichiarato come \texttt{Boolean}: Gson lancia una
\texttt{IllegalStateException} (\emph{``Expected a boolean but was NUMBER''}) durante
la deserializzazione di ogni esame. L'eccezione veniva inghiottita silenziosamente
dal blocco \texttt{runCatching} in \texttt{refreshEsami()}, impedendo
completamente il popolamento di Room con i dati del server --- lo stesso punto
di fallimento del bug sulla data ISO~8601, ma con una causa diversa.

\paragraph{Soluzione}
Il tipo del campo \texttt{lode} in \texttt{ExamDto} è stato modificato da \texttt{Boolean}
a \texttt{Int}. Nei punti del codice in cui il DTO viene mappato a \texttt{EsameEntity}
(inserimento e aggiornamento in \texttt{refreshEsami()}), la conversione esplicita
\texttt{dto.lode != 0} produce il valore booleano atteso. \texttt{ExamRequest.lode}
rimane \texttt{Boolean}: Gson lo serializza correttamente come \texttt{true}/\texttt{false}
e lo schema Zod del backend accetta valori booleani in ingresso.

\section{Visibilità degli errori silenti nel layer di rete}

\paragraph{Problema}
Il layer dati conteneva circa dieci blocchi \texttt{runCatching} che inghiottivano
ogni eccezione senza alcun log. Tre bug distinti (data ISO~8601, ENUM tema\_voti,
lode TINYINT) erano rimasti latenti per settimane perché nessun messaggio di errore
appariva nel Logcat. La diagnosi richiedeva di collegare un debugger e impostare
breakpoint manualmente, rendendo il ciclo di debug molto lento.

\paragraph{Soluzione}
Aggiunto il callback \texttt{.onFailure \{ e ->} \texttt{Log.e(TAG, "...", e) \}} a ogni blocco
\texttt{runCatching} critico nei repository (\texttt{EsameRepositoryImpl},
\texttt{ObiettivoRepositoryImpl}, \texttt{SettingsRepositoryImpl}). Il tag
per ogni repository è una costante \texttt{private const val TAG} dedicata:
filtrare il Logcat per \texttt{EsameRepository}, \texttt{ObiettivoRepository}
o \texttt{SettingsRepository} mostra immediatamente ogni chiamata API con
il suo esito. Per il traffico HTTP raw (header, body, status code) è già
attivo \texttt{HttpLoggingInterceptor.Level.BODY} in \texttt{NetworkClient}:
filtrare per tag \texttt{OkHttp} nel Logcat espone l'intera comunicazione
con il server senza alcuna modifica al codice.

\section{Risposta HTTP non vuota su endpoint che non restituiscono dati}

\paragraph{Problema}
Due endpoint del backend --- \texttt{DELETE /exams/:id} e \texttt{POST /auth/logout}
--- rispondono con un corpo JSON di conferma (\texttt{\{"message":"..."\}}) anziché
un corpo vuoto. In Retrofit~2, dichiarare il tipo di ritorno come
\texttt{Response<Unit>} fa sì che il convertitore Gson tenti di deserializzare
quel corpo come \texttt{Unit}; su corpi non vuoti questo produce un'eccezione a
runtime.

Per il DELETE l'impatto era funzionale: il blocco \texttt{runCatching} nel metodo
\texttt{deleteEsame()} di \texttt{EsameRepositoryImpl} catturava l'eccezione e
restituiva \texttt{null}; il controllo di successo della response risultava quindi
\texttt{false}. L'app chiamava \texttt{markPendingDelete} invece di eliminare la riga
da Room, lasciando l'entità con \texttt{pendingDelete = true} anche se il server aveva
già eliminato l'esame. L'esame spariva dalla UI (filtro \texttt{pending\_delete = 0}),
ma \texttt{SyncExamsWorker} doveva eseguire un ciclo di retry aggiuntivo.

Per il logout l'impatto era nullo dal punto di vista dell'utente: l'eccezione
veniva comunque inghiottita da \texttt{runCatching} e il codice successivo
(\texttt{clearCookies}, \texttt{clearAllTables}, \texttt{setLoggedIn(false)})
veniva eseguito regolarmente. Tuttavia la chiamata \texttt{POST /auth/logout}
non veniva completata correttamente lato OkHttp (connessione non rilasciata).

\paragraph{Soluzione}
Entrambi i metodi sono stati cambiati da \texttt{Response<Unit>} a
\texttt{Response<ResponseBody>}, in analogia con il metodo \texttt{updateSettings()}
già presente in \texttt{SettingsApiService}. Il corpo viene chiuso
esplicitamente con \texttt{body()?.close()} per rilasciare la connessione
OkHttp; nessun campo del corpo viene letto poiché non è necessario.

\begin{lstlisting}
// AuthApiService.kt
@POST("auth/logout")
suspend fun logout(): Response<ResponseBody>

// ExamApiService.kt
@DELETE("exams/{id}")
suspend fun deleteEsame(@Path("id") id: Int): Response<ResponseBody>

// AuthRepositoryImpl.kt
runCatching { apiService.logout() }.getOrNull()?.body()?.close()

// EsameRepositoryImpl.kt
if (response?.isSuccessful == true) {
    response.body()?.close()
    dao.deleteEsame(entity)
}
\end{lstlisting}

\section{Allineamento dei nomi di campo nelle risposte di aggiunta e modifica esame}

\paragraph{Problema}
Le risposte JSON del backend per \texttt{POST /exams} e \texttt{PUT /exams/:id}
usano la convenzione \textit{snake\_case} per i campi opzionali
(\texttt{xp\_totali\_guadagnati}, \texttt{nuovi\_badge}, \texttt{badge\_revocati},
\texttt{xp\_difference}), mentre i corrispondenti data class Kotlin
(\texttt{AddExamResponse}, \texttt{UpdateExamResponse}) usavano i nomi
camelCase senza annotazioni \texttt{@SerializedName}.
Gson non trovava corrispondenza e popolava sempre quei campi con \texttt{null},
impedendo a potenziali consumatori futuri di leggere i dati restituiti dal server.

\paragraph{Soluzione}
Aggiunte le annotazioni \texttt{@SerializedName} ai campi coinvolti, allineando
la deserializzazione Gson al contratto del backend:

\begin{lstlisting}
data class AddExamResponse(
    val ids: List<Int>,
    @SerializedName("xp_totali_guadagnati") val totalXp: Int?,
    @SerializedName("nuovi_badge") val newBadges: List<Any>?
)

data class UpdateExamResponse(
    @SerializedName("nuovi_badge") val newBadges: List<Any>?,
    @SerializedName("badge_revocati") val revokedBadgeIds: List<Any>?,
    @SerializedName("xp_difference") val xpDifference: Int?
)
\end{lstlisting}

\section{Sincronizzazione unidirezionale delle impostazioni utente}

\paragraph{Problema}
Le impostazioni utente (tema voti, soglie RGB) erano sincronizzate correttamente
nella direzione mobile~$\rightarrow$~web: la funzione \texttt{saveSettings()} invocava
\texttt{updateSettingsUseCase()}, che aggiornava il DataStore locale e chiamava
\texttt{PUT /settings} sul backend.
La direzione opposta, web~$\rightarrow$~mobile, era però interrotta:
\texttt{getSettingsUseCase()} veniva chiamato una sola volta al momento della
creazione del \texttt{ProfiloViewModel} (nel blocco \texttt{init~\{\}}), e
\texttt{observeSettingsUseCase()} osservava esclusivamente il DataStore locale.
Di conseguenza, qualsiasi modifica effettuata tramite l'interfaccia web non veniva
mai recepita sull'app mobile finché l'utente non eseguiva logout e ri-login,
oppure non forzava la chiusura dell'app.

\paragraph{Soluzione}
Il pattern già adottato in \texttt{LibrettoScreen} — un \texttt{LaunchedEffect(Unit)}
che recupera i dati dal server ad ogni ingresso nella schermata — è stato applicato
anche a \texttt{ProfiloScreen}.
Ogni volta che l'utente naviga alla schermata Profilo, il blocco esegue
\texttt{viewModel.loadSettings()}, che interroga il backend e aggiorna il DataStore;
\texttt{observeSettingsUseCase()} reagisce automaticamente all'aggiornamento e la
UI mostra i valori più recenti.

\begin{lstlisting}
// ProfiloScreen.kt
LaunchedEffect(Unit) { viewModel.loadSettings() }
\end{lstlisting}

La chiamata è idempotente e ha un costo trascurabile: il backend restituisce un
payload JSON minimo e il DataStore viene aggiornato solo se i valori sono cambiati.
Il \texttt{loadSettings()} nell'\texttt{init~\{\}} del ViewModel è stato mantenuto
per garantire il caricamento immediato alla prima apertura dell'app, prima che
la composizione della schermata raggiunga il \texttt{LaunchedEffect}.

% ── CAPITOLO 4 — PUNTI FORTI E PUNTI DEBOLI ─────────────────
\chapter{Punti Forti e Punti Deboli}

\section{Punti Forti}

\begin{itemize}
    \item \textbf{Modulo \texttt{:domain} puro Kotlin}: nessuna dipendenza Android
    nel layer di business logic. I Use Cases e i calcoli statistici sono testabili
    su qualunque JVM senza emulatore, con tempi di esecuzione del test suite inferiori
    ai 5 secondi.

    \item \textbf{UI interamente reattiva}: la UI non interroga mai i dati in modo
    attivo. Ogni aggiornamento (nuovo esame, cambio XP, modifica impostazioni) viene
    propagato automaticamente da Room tramite \texttt{Flow} fino al composable,
    senza polling né notifiche manuali.

    \item \textbf{Strategia offline-first robusta}: i flag \texttt{pendingSync} e
    \texttt{pendingDelete} su \texttt{EsameEntity} coprono l'intero ciclo di vita
    CRUD anche senza connessione. Le eliminazioni fallite vengono nascoste dalla UI
    (\texttt{getAllEsami} filtra \texttt{pending\_delete = 0}) e ritentate da
    \texttt{SyncExamsWorker} al ritorno della rete, anche con l'app chiusa.

    \item \textbf{Token refresh trasparente}: \texttt{TokenAuthenticator} gestisce
    il rinnovo del JWT senza che nessun ViewModel o Use Case ne sia consapevole.
    Il codice applicativo non contiene mai logica di retry per gli errori 401.

    \item \textbf{Navigazione adattiva senza codice condizionale}: \texttt{NavigationSuiteScaffold}
    adatta automaticamente la navigazione al form factor (smartphone, tablet, desktop
    windowing) senza un singolo \texttt{if} sul tipo di schermo.

    \item \textbf{Factory pattern uniforme sui ViewModel}: tutti i ViewModel usano
    \texttt{ViewModelProvider.Factory} con DI manuale, garantendo testabilità omogenea
    e coerenza con il pattern insegnato dal corso.
\end{itemize}

\section{Punti Deboli}

\begin{itemize}
    \item \textbf{DI manuale non scalabile}: il pattern \texttt{RepositoryProvider}
    funziona per il perimetro attuale, ma con l'aggiunta di nuovi repository o
    dipendenze trasversali diventa verboso. Hilt sarebbe preferibile su un progetto
    di dimensioni maggiori.

    \item \textbf{Test di integrazione assenti}: Room DAO e \texttt{CoroutineWorker}
    non sono coperti da test automatici (richiedono rispettivamente un database
    in-memory e l'infrastruttura \texttt{WorkManagerTestInitHelper}). La copertura
    del test suite si ferma al layer domain e ViewModel.

    \item \textbf{Gestione errori di rete non granulare}: gli errori di rete
    (\texttt{IOException}), di timeout e di risposta server (4xx/5xx) vengono mappati
    sulla stessa classe \texttt{Error} nella UI. Una gerarchia di errori distinta
    permetterebbe messaggi più precisi all'utente.

    \item \textbf{\texttt{SharingStarted.Eagerly} in \texttt{LibrettoViewModel}}:
    solo \texttt{LibrettoViewModel} usa \texttt{Eagerly} --- scelta deliberata per
    mantenere il Flow di Room sempre attivo e garantire la disponibilità immediata
    della lista al rientro in composizione. Gli altri ViewModel
    (\texttt{GamificationViewModel}, \texttt{StatisticheViewModel},
    \texttt{ObiettiviViewModel}) adottano \texttt{WhileSubscribed(5000)}, che
    sospende l'upstream dopo cinque secondi senza sottoscrittori, ottimizzando
    le risorse. Il trade-off è accettabile per le dimensioni del progetto attuale.
\end{itemize}

% ── CAPITOLO 5 — MIGLIORIE E SVILUPPI FUTURI ────────────────
\chapter{Migliorie e Sviluppi Futuri}

\section{Migliorie a Breve Termine}

\begin{itemize}
    \item \textbf{Test di integrazione per Room}: aggiungere test con database
    in-memory per verificare query DAO, migration e comportamento del \texttt{Flow}
    al variare dei dati persistiti.
    \item \textbf{Gerarchia di errori di rete}: distinguere \texttt{NetworkError}
    (assenza di connessione), \texttt{TimeoutError} e \texttt{ServerError} per
    mostrare messaggi contestuali e strategie di retry differenziate nella UI.
    \item \textbf{Accessibilità}: completare i \texttt{contentDescription} su tutti
    gli elementi interattivi dei composable per il supporto agli screen reader.
    \item \textbf{Indicizzazione Room}: aggiungere \texttt{@Index} sulle colonne
    \texttt{remote\_id}, \texttt{pending\_sync} e \texttt{pending\_delete} di
    \texttt{EsameEntity}, utilizzate frequentemente dal \texttt{SyncExamsWorker}
    per le query di filtering.
\end{itemize}

\section{Sviluppi Futuri}

\begin{itemize}
    \item \textbf{Notifiche Push via FCM}: sostituire le notifiche locali del worker
    \texttt{LeaderboardCheckWorker} con push server-side,
    eliminando il polling periodico dal dispositivo.
    \item \textbf{Widget home screen}: visualizzazione rapida di media ponderata e
    livello XP senza aprire l'app, tramite Glance API (Jetpack Compose per widget).
    \item \textbf{Importazione piano di studi}: integrazione con le API di Esse3 o
    Almaesami per pre-popolare il libretto con gli esami del piano di studi ufficiale.
    \item \textbf{Dependency Injection con Hilt}: migrazione da \texttt{RepositoryProvider}
    manuale a Hilt per migliorare la scalabilità del progetto e ridurre il boilerplate
    nelle factory dei ViewModel.
\end{itemize}
